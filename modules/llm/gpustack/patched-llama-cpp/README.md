# Patched llama.cpp build for gpustack-legacy

This directory holds the build + deploy scripts for a custom-patched llama.cpp
Vulkan binary that fixes the SWA-prompt-cache crash on AMD Strix Halo with
gemma4. Applied 2026-05-12. See memory
`project_gemma4_swa_prompt_cache_patched_build.md` and
`.gsd/milestones/M031/M031-ROADMAP.md` (S5).

## What's in here

- `22458.patch` — the upstream patch (PR #22458) source
- `build.sh` — builds llama-server + libs from llama.cpp@b9112 + patch in a
  transient ubuntu:24.04 container. Idempotent. ~5-10 min on a modern box.
- `deploy.sh` — installs the built artifacts into a running gpustack
  container, restarts gpustack so all 6 model children spawn with the
  patched binary. Calls `build.sh` automatically if binaries are missing.
- `README.md` — this file

The compiled artifacts (`llama-server`, `lib*.so*`) are NOT committed —
they're regenerated by `build.sh` and live in `.gitignore`.

## What the patch does

Upstream PR #22458 (closed/unmerged due to procedural reasons) modifies
`ggml/src/ggml-backend.cpp` so that `ggml_backend_tensor_set` and
`ggml_backend_tensor_get` no longer assert when `tensor->data == NULL`.
On Vulkan + unified-memory APUs, SWA-layer KV tensors can legitimately
have a NULL host-side data pointer (device-only buffer). The original
assertion fired during `llama_io_write_host::~llama_io_write_host` →
`llama_context::state_seq_get_data` → `ggml_backend_tensor_get`,
i.e. the per-slot prompt cache save path. With the patch, that path
falls through to the backend's `iface.get_tensor` which handles the
device read without a host pointer.

The patch is 16 lines, surgical, only touches one file. The two affected
functions get an early-return branch.

## How to use

```bash
# From this dir:
./deploy.sh                                     # builds (if needed) + deploys to local container 'gpustack'
GPUSTACK_CONTAINER=gpustack-legacy ./deploy.sh  # different container name

# Or remote (worker box):
scp -r llm/gpustack/patched-llama-cpp worker:/tmp/
ssh worker '/tmp/patched-llama-cpp/deploy.sh'   # builds inside ubuntu:24.04 container on worker
```

The build runs inside a transient `ubuntu:24.04` container so it works on any
host with Docker. Output: ~10 min depending on cores.

## Choice of base tag

**b9112** specifically because:
- Newer than b9101 (the patch's `ggml-backend.cpp` line numbers match)
- Older than b9120+ which use cooperative-matrix-2 Vulkan extensions Ubuntu
  24.04's stock `libvulkan-dev` doesn't have
- Compiles cleanly on Ubuntu 24.04 with `libvulkan-dev` + `glslc` + `spirv-headers`
- Glibc-compatible: built on Ubuntu 24.04 (glibc 2.39) runs fine in
  gpustack's rocm-terminal:6.4 base (Ubuntu 22.04, glibc 2.35) — verified

## What deploy.sh does

1. Backs up current binaries to `/tmp/llama-backup/` inside the container
2. Copies `llama-server` + all `.so*` files into the gpustack llama-box-default dir
3. Re-creates the `.so` and `.so.0` symlinks that were lost in transit (so
   dlopen of `libfoo.so.0` resolves correctly)
4. Sanity-checks the new binary with `--version`
5. Restarts gpustack so all 6 model children spawn with the patched binary

The wrapper script at `$DIR/llama-box` is preserved — it strips `--no-mmap`
and `--no-warmup` for our Strix Halo memory model.

## Rollback

```bash
DIR=/usr/local/lib/python3.10/dist-packages/gpustack/third_party/bin/llama-box/llama-box-default
docker exec gpustack cp /tmp/llama-backup/* $DIR/
docker restart gpustack
```

Or rebuild the gpustack image from scratch (`docker compose build gpustack`)
which restores the upstream b9101 binary from the GitHub release tarball.

## Long-term plan

Once upstream merges a real fix (or a successor PR to the closed
#22453/#22458), drop this entire patched-build pipeline and revert to
upstream binaries. Tracked in M031-S5.

## BSB-08 — patched build is now baked into the image

As of BSB-08 (Half-B LOW, 2026-05-15), the patched llama.cpp build is
also baked INTO the legacy `Dockerfile.vulkan` as a builder stage
(`patched-llamacpp-builder`). Every `docker compose --profile llm-legacy
build gpustack-legacy` reproduces the patched binaries from this same
`22458.patch` source.

The hot-cp path (`./build.sh && ./deploy.sh`) is preserved for two
operational use cases:

1. **Hot-fix on a running container without rebuild** — useful when
   waiting for an image rebuild + push cycle is unacceptable.
2. **Worker boxes that can't rebuild** — a worker box may not have the
   build context, so deploy.sh's "scp dir + ssh deploy" pattern is the
   shortest path to the patched binary on remote nodes.

The image-baked binaries are the source of truth for fresh installs;
deploy.sh is the override path. Both produce the same `llama-server`
binary from the same `22458.patch`.

After every image rebuild, verify the patched binaries are in place
without running `--version`:

```bash
docker exec gpustack cat /etc/razzfazz/llama-cpp-patch.json
# {"llama_cpp_tag":"b9112","upstream_pr":22458,
#  "patch_sha256":"...","build_date":"...","baked_in":true}
```

The acceptance test
`tests/acceptance/gpustack_legacy/test_patched_llamacpp_baked.py`
enforces this contract on every test run.
